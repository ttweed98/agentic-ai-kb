## What changed since the project was designed

### ★★ E1 has been answered in public, by AWS

Dogwood's launch post works the experiment: an agent capped at $5,000/hour issues concurrent
$2,000 transfers, each passes individually, the aggregate does not. **Their named fix: count
request events including in-flight ones, not response events.**

And `dogwood-local-engine` **1.0.0 shipped 2026-09-29** — redb-backed durable log, periodic
snapshots, fsync before verdict, and *"a lock that admits one submission at a time"* to
linearize concurrency. Crash recovery = snapshot + replay.

⚠ **E1 as originally written is no longer novel.** Two reframings that are:

- **E1a — does the Local Engine's linearization claim hold?** AWS asserts it. Nobody has
  tested it independently. Same design, measuring their implementation rather than the
  absence of one.
- **E1b — does request-vs-response counting actually fix it?** AWS names this as *the* fix.
  Two arms, one variable, directly testable. This is the better experiment.

**Prior art in the wild:** `yunaremaia/agent-guard` **issue #136, 2026-09-21**, closed and
labelled a security vulnerability — `Guard.check()` non-atomic read-modify-write lets
concurrent threads lose increments, so `max_tool_calls` is silently bypassed. Fix was a
`threading.Lock()`. Siblings: #92 (counter increments on *denied* calls → premature
enforcement) and #62 (sliding-window request). **This is the failure mode, observed, three
weeks ago.**

### ★ Batfish ships a first-party MCP server — this removes work

`pip install 'pybatfish[mcp]'` → `batfish-mcp`. 36 tools at release, more since (PR #995
merged 2026-09-29 added `generate_dataplane`, `get_lpm_routes`, `get_edges`, `get_server_info`).

`run_traceroute` / `run_bidirectional_traceroute` gained **`trace_format: text | structured |
summary`** — structured JSON traces mean hop extraction with no regex parsing.

PR #995's stated motivation: results were **exceeding the MCP tool-result limit** on large
snapshots. Someone is building real agents against this and hitting real limits.

⚠ Release notes warn *"tool names and parameters may still change."*

**Consequence: the predicate tool is not something to build. It exists, it is Apache-2.0, and
it is also a working reference implementation of a network-domain MCP server** — worth reading
for its own sake (`pybatfish/mcp/server.py`).

Batfish is **not abandoned**. AWS-managed since the Intentionet team joined. Java-side majors
are roughly annual and irregular; pybatfish ships often. Do not read the Java cadence as death.

### ⚠ Grafana's agent product is not what the marketing says

**Grafana Agent Observability** GA'd 2026-07-30 and is pitched as a fifth telemetry signal —
agent sessions, evals, policy enforcement, blocking dangerous tool calls.

Three facts from Grafana's own docs:

1. **Grafana Cloud only.** The what's-new entry states plainly: *"No self-managed release."*
2. **Not OTel.** Generation data goes to a proprietary endpoint (`AGENTO11Y_ENDPOINT` with
   `AGENTO11Y_AUTH_TOKEN`) via Grafana's own SDKs. OTel traces travel a separate optional path.
3. The 8 "Agent Observability" tools in `mcp-grafana` (disabled by default) query **that Cloud
   service**, not your Tempo.

⇒ **Unusable for a self-hosted build.** The viable path is below.

## Decisions

### Observability — plain OTel, self-hosted, no platform

**Instrument with the bare OTel SDK → Alloy → Tempo / Mimir / Loki. Query with TraceQL.**

- Tempo stores `gen_ai.*` spans as ordinary OTLP spans; TraceQL filters them like anything else.
- **Tempo 2.9+ ships its own MCP server** over TraceQL (experimental) — the agent can query
  its own traces.
- `grafana/mcp-grafana` **v1.3.0 · 2026-08-28, Apache-2.0**, ~90–130 tools, covers Prometheus,
  Loki, dashboards, alerting. v1.3.0 gates raw-SQL tools behind `--disable-write` by default.

**The conventions, and the catch.** All `gen_ai.*` attributes are status **`Development`** —
nothing is Stable. Worse: in semconv **v1.42.0 (2026-06-12)** the GenAI material moved out of
`open-telemetry/semantic-conventions` into **`open-telemetry/semantic-conventions-genai`**,
and that repo has **zero releases and zero tags**. ⇒ **Nothing to pin but a commit SHA.**

Attributes that matter here:

- `gen_ai.operation.name` ∈ { `chat`, `execute_tool`, `invoke_agent`, `plan`, … }
- `gen_ai.tool.name`, `gen_ai.tool.type`, `gen_ai.tool.call.id`, `gen_ai.tool.call.arguments`,
  `gen_ai.tool.call.result`
- `gen_ai.agent.name`, `gen_ai.conversation.id`
- ★ **MCP has its own conventions** (`docs/gen-ai/mcp.md`, Development):
  `mcp.method.name`, `mcp.resource.uri`, `mcp.protocol.version`, `mcp.session.id` —
  covering `tools/call`, `tools/list`, `resources/read`, `initialize`, and notifications.

⚠ **Renames already happened:** `gen_ai.system` → `gen_ai.provider.name`;
`prompt_tokens`/`completion_tokens` → `input_tokens`/`output_tokens`; `gen_ai.prompt` and
`gen_ai.completion` **removed**. Expect more.

⚠ **`gen_ai.input.messages` / `output.messages` are Opt-In and should stay off** — device
configs in prompts would otherwise land in Tempo.

★ **Set `gen_ai.conversation.id` to a change or incident number** and the whole agent run is one
retrievable trace. That is the single highest-value instrumentation decision.

**Platforms, if ever needed:** every one of Langfuse (MIT), Arize Phoenix (ELv2), LangSmith,
Braintrust, W&B Weave and OpenLIT (Apache-2.0) now ingests **plain OTLP**. None is
framework-locked any more. So instrumenting with bare OTel keeps all of them as drop-in later
options without re-instrumenting. W&B Weave has one disqualifying gap for this use case: its UI
**does not render OTel tool calls** — they appear as raw JSON.

### Policy — Dogwood by sidecar, Cedar as the shipping path

★ **`dogwood-server` exists and AWS's blog does not mention it.** A sibling crate in the
`dogwood-local-engine` workspace, described in the repo README as a demo service that
**listens on two Unix sockets — a control plane for policy-set modifications and a data plane
for history and decision events.** `event_to_json` / `event_from_json` in the engine's public
API strongly suggest JSON framing.

⚠ The wire format is **not documented**. Reading `dogwood-server/src/` once and writing an
asyncio Unix-socket client is roughly 150 lines. Risk: it is labelled a *demo*, so this may
mean maintaining a fork.

**Rejected alternatives and why:**

| Option | Verdict |
|---|---|
| `dogwood-py` 0.0.11.dev33 | ⚠ **No.** One person's dev release, binds the **reference interpreter** which AWS says is *"NOT intended for production use"* — in-memory, no eviction, lost on restart |
| Hand-written PyO3 binding | No. That is a Rust project with manylinux wheels and ABI maintenance forever |
| Reimplement the temporal macros | No. The semantics *are* the value, and AWS's benchmarks show a 24h window is ~300× slower than 15min — they have done non-trivial incremental-monitor work |
| **Cedar + own locked counter store** | **Viable, and the shipping path.** Dogwood lowers to Cedar by design, so Cedar covers the non-temporal half for free. SQLite with proper transactions covers modest temporal needs. Days, not weeks — but you inherit every concurrency bug |

**Cedar practicals:** 4.13.0 · 2026-09-15. Python via **`cedarpy` 4.12.1 · 2026-09-24** —
community (k9securityio), explicitly *not* AWS-supported, but tracks upstream within ~2 months
and exposes `is_authorized`, `is_authorized_batch`, **`is_authorized_partial`**, template
linking.

★ **`cedar-policy/cedar-for-agents` is official AWS** — generates Cedar schemas **from MCP tool
definitions**, so tool calls become typed Cedar requests. That is exactly the seam `preflight`
sits on. Includes `cedar-analysis-mcp-server`.

Also: **Strands Agents SDK ships an official Cedar authorization intervention** in Python —
evaluates Cedar before each tool call, user → principal, tool name → action, args → context,
**fail-closed**. Exposes `context.session.call_count`, a bare counter rather than a history
query. Worth reading as prior art even if not adopted.

**OPA is the fallback, not the choice.** Healthy (CNCF Graduated, 1.21.x) but no Python SDK —
sidecar HTTP or community WASM. More importantly: **OPA decides, it never reserves.** No
atomicity primitive, so any aggregate limit built on it is read-only against state something
else must update. The published pattern worth knowing is Vercel AI SDK's **Policy-Based Tool
Approvals** — Rego before every tool dispatch, mapped to allow / deny / requires-approval /
not-applicable.

### Compliance rules — build the runner, borrow the corpus

★★ **The unlock: Netpicker's rule corpus is open source even though the runner is not.**
`netpicker/pytests-for-networking` is public — `CIS/`, `CVEasy_examples/`, `Integrations/`,
`tests/`. The assert bodies are plain Python:

```python
@low(name='rule_banner_check', platform=['cisco_ios'])
def rule_banner_check(configuration):
    assert 'Authorized access only' in configuration
```

Strip the decorator, supply `configuration` / `commands` yourself, and these port to plain
pytest in an afternoon. **A free rule library, not a free runner.**

⚠ **KB correction.** `sources/netpicker-rule-syntax.md` implies the rules are standalone
pytest. They are not — the `@low` / `@medium` / `@high` decorators and the injected
`configuration` / `commands` / `device` / `devices` parameters are Netpicker-supplied globals.
There is no documented way to run a rule outside the product.

⚠ **Commercially blocked anyway.** Foundation is free for backup/search but caps *Professional
features including compliance validation at 10 devices*. Professional starts at **$7,500/yr**,
Enterprise at **$33,500/yr**.

**What was evaluated and rejected as the rule engine:**

| Option | Why not |
|---|---|
| Nautobot Golden Config | Prefix line-matching only — *"the match is based on what a line starts with"*. No conditionals, no numeric comparison, no negation, no cross-device relationships. **Use it for intended-config data, not as the rule language** |
| SuzieQ | 0.24.0 · **2025-05-09** — 17 months stale, 114 open issues, 21 open PRs. `assert` is a fixed built-in on four tables, **not user-definable**. Use the query API as a state source if at all |
| pyATS / Genie | Apache-2.0, healthy, Cisco-funded — but **Linux/macOS wheels only, no Windows**, and ~25% of the core is compiled closed-source Cython |
| NAPALM `compliance_report()` | Works (`assert report["complies"]`) but rules are YAML, not Python |
| NUTS | 3.6.0 · 2024-05-17. Dormant |
| netlint | 0.1.2 · **2021**. Dead, and GPL-3.0 — a vendoring problem |
| OPA / CUE over config data | Healthy, but the hard part is the parse step and they buy nothing over Python asserts once you've done it |

**The shape that works:** plain pytest asserts over `ciscoconfparse2` / `hier_config` for text,
and **pybatfish for semantics**. That is the Netpicker rule shape minus the decorator, and it is
small code.

### Nautobot → agent — build it

⚠ **Correction to an earlier note:** Network to Code *does* ship an official
`nautobot-mcp-server`, **v1.1.0 · 2026-09-08** — but it is distributed through **private
Artifactory** (`nautobot.jfrog.io`, credentials required) and is part of the commercial
NautobotAI bundle. Docs are public at `docs.nautobot.com/projects/nautobot-mcp-server/`; the
package is not.

Its design is worth copying: **bearer token validated against Nautobot's API per request, so it
honours Nautobot RBAC**, read-only with no mutations exposed, streamable-HTTP.

**Community options:**

| Repo | State |
|---|---|
| `bsmeding/nautobot-mcp-server` | 0.2.2 · 2026-09-15. Best prior art — generic REST + GraphQL, read-only by default, **tenant scoping**, plugin tools for GC/SSoT/Design Builder, pagination caps. ⚠ **2 stars, single maintainer, and the licence is ambiguous — PyPI says MIT, the repo `LICENSE` is an unfilled Apache-2.0 template.** That is a blocker for any employer legal review |
| `gt732/nautobot-app-mcp` | **Archived 2025-05-27.** Do not build on it |
| `kvncampos/nautobot_mcp`, `aiopnet/mcp-nautobot` | Toy-scale |

★ **Verdict: build it. One to three days for something usable, a week to make it good.**

Nautobot exposes an OpenAPI/`drf-spectacular` schema and a GraphQL endpoint. A schema-driven
`rest_list`/`rest_get` pair plus `graphql_query` covers ~90% of what a change-checking agent
asks. `pynautobot` handles pagination, filtering and auth. The MCP side is boilerplate —
⚠ **write against mcp 2.x `MCPServer`, not 1.x `FastMCP`.**

The hard parts are not MCP-specific: a read-only guarantee you trust, tenant scoping enforced
server-side, response-size control so a device list does not blow the context window, and tool
descriptions good enough that the model picks correctly.

★ **Read `bsmeding`'s tenant-scope and pagination-cap implementation first** — it has solved
two of those four already.

## ★ Three things that do not exist — build candidates

Per the standing position that a gap is a candidate, not a blocker. All three are small, real,
and have no good open-source answer today.

| # | Thing | Size | Why it is worth doing |
|---|---|---|---|
| **BC1** | **An open-source Nautobot MCP server** | 1–3 days | The official one is commercial and behind private Artifactory; the only community option is 2 stars with an ambiguous licence. There is a real audience |
| **BC2** | **An open compliance-rule runner** — Netpicker's rule shape, standalone | days | The corpus is already open; only the runner is missing. Porting it makes a $7,500/yr feature free, and the rules are plain `assert`s |
| **BC3** | **A Python client for `dogwood-server`** | ~150 lines + a read of the Rust | Nobody has one. The only Python path to Dogwood today binds the engine AWS says not to run |

★ **BC2 is the strongest of the three** — smallest, most immediately useful, and it lands
directly on Q5 (does a rule expressed as code bind?) with a real corpus to test against.
